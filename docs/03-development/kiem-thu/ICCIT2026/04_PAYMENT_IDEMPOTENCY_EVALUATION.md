# Payment IPN Idempotency Evaluation

## Implemented control

Paid finalization is wrapped by a MySQL named lock keyed by `provider_ref`. Inside the lock, an already-paid payment returns without repeating order, transaction, booking or subscription side effects. A `payment_events` row records the paid transition where that table is available. Existing terminal-state handling remains in `markPaymentStatus`.

The lock is applied to VNPay, MoMo, mock, PayPal and Stripe finalization call paths that use `finalizePaid`.

## Executed evidence

`backend/tests/payment-idempotency.no-db.test.js` mocks the database and invokes the finalizer twice for the same provider reference. It verifies one event and one set of downstream side effects. The expanded focused run passed **4 suites, 29 tests**.

The database-backed VNPay integration test uses the actual `GET /api/payments/vnpay/return` callback route, HMAC-SHA512 test signatures and real MySQL `beautycare_test`. One normal callback, one sequential duplicate, three repetitions of 50 concurrent duplicates, one late failure callback and one tampered amount were executed. Each concurrent repetition produced 50 HTTP 302 redirects and exactly one paid event and one transaction; the tampered callback left the payment `created`, the order `pending`, and produced zero paid events/transactions. Raw evidence is `raw-results/vnpay-idempotency/vnpay-duplicate-callback-20261021.json` and the detailed report is `13_VNPAY_DUPLICATE_CALLBACK_INTEGRATION.md`.

## Sandbox evidence and remaining limit

The retained VNPay sandbox evidence contains 11 DB-verified attempts: 10 `paid` and 1 `failed`, with no stored secrets or card data. It is documented in `results/vnpay-sandbox/transaction-summary.json` and was reviewed separately from the isolated regression run.

The duplicate callback/retry path is now verified against the application callback route and isolated real MySQL, but it was not replayed through the live VNPay provider. The live provider delivery/network behavior remains a limitation. No production callback was used.

## Final route-verification correction

The source now verifies that a VNPay Return callback references a persisted VNPay payment and that `vnp_Amount` equals the stored amount multiplied by 100. The new regression case uses a valid HMAC with a mismatching persisted amount and observes `payment=created`, `order=pending`, `paidEvents=0`, and `transactions=0`. The latest full-suite artifact records concurrent durations of 249 ms, 210 ms, and 266 ms. This historical Return-only statement predates the subsequent VNPay IPN implementation; current IPN evidence is documented separately and must not be merged with the earlier Return-only artifact.
