# ICCIT 2026 — VNPay IPN Implementation and Performance

## Status

VNPay IPN is implemented locally for the existing VNPay integration. The browser Return URL remains a redirect flow; IPN is a server-to-server JSON acknowledgement and does not redirect the browser. Both `GET /api/payments/vnpay/ipn` and `POST /api/payments/vnpay/ipn` are exposed because the project’s Sandbox-compatible configuration uses GET while deployments may use POST.

The implementation verifies the HMAC-SHA512 signature, transaction reference, persisted provider, amount in minor units, and transaction result. Successful callbacks use the shared payment finalization path. Finalization is protected by a provider-reference named lock and a transaction on the same MySQL connection, preventing the lock/transaction pool deadlock observed during the first independent-payment load attempt. Terminal payments return VNPay duplicate code `02`; invalid signature, reference, and amount return `97`, `01`, and `04`; temporary processing errors return `99`.

## Integration evidence

The isolated MySQL test `beautycare_test` covered valid IPN, sequential duplicate, three repetitions of 50 concurrent duplicate callbacks, invalid signature, invalid amount, invalid reference, failed transaction, IPN/Return race, and injected failure followed by retry. The raw artifact records the provider response and final payment/order/event/transaction state for each scenario:

`raw-results/vnpay-ipn/vnpay-ipn-20261021.json`

The latest raw artifact records concurrent integration durations of 263 ms, 270 ms, and 277 ms. Each repetition ended with one paid event and one transaction. The invalid signature and amount cases caused no payment side effects. The IPN/Return race also ended with one paid event and one transaction.

## k6 callback workload

The signed fixtures were generated by `backend/scripts/prepare-k6-vnpay-ipn.js` using a test-only secret supplied out-of-band. The secret value is absent from the fixture and raw result. k6 was run in Docker using `grafana/k6:2.3.0`, against the local backend on port 3010 and only the `beautycare_test` database.

P1 used one persisted payment reference and measured duplicate delivery with 100 VUs for 30 seconds. The successful rerun produced 86,584 callbacks: 100 initial confirmations and 86,484 duplicate responses; unexpected responses were 0. The observed callback latency was average 34.497993244248214 ms, p50 32.1110365 ms, p90 39.125327899999995 ms, p95 41.71110094999999 ms, and p99 49.582684009999994 ms. The raw k6 summary is `results/k6-vnpay-ipn-p1-p1-run2.json`.

P2 used 100 independent signed payment fixtures and one callback per VU within the 30-second window. It produced 100/100 confirmed responses and 0 unexpected responses. The observed latency was average 300.4298795 ms, p50 307.14601749999997 ms, p90 396.513007 ms, p95 397.9607818 ms, and p99 398.63918035 ms. The raw k6 summary is `results/k6-vnpay-ipn-p2-p2-run6.json`.

The first P1 attempt was intentionally retained as a provenance failure: the fixture secret did not match the server environment and all callbacks were rejected as invalid signatures. The first P2 attempt exposed a real pool exhaustion/deadlock risk when the named-lock connection and transaction used different connections. Neither attempt is included as a successful benchmark result. The implementation was corrected and the focused IPN/atomicity tests passed before the successful reruns.

## Academic result statement

*A VNPay IPN handler was implemented and evaluated against an isolated MySQL test database. The handler verified HMAC-SHA512 signatures, transaction references, provider identity, amount consistency, and terminal-state idempotency while separating server-side acknowledgement from the browser Return redirect. The integration experiment recorded one paid event and one transaction for each of three 50-callback duplicate repetitions, while invalid signature and amount cases produced no payment side effects. In a Dockerized k6 workload with 100 virtual users for 30 seconds, the duplicate-delivery profile processed 86,584 callbacks with 100 initial confirmations and 86,484 duplicate acknowledgements; the independent-payment profile processed 100/100 confirmations. These observations support a bounded local claim about application-level callback idempotency and consistency, not a claim about live VNPay delivery or production network performance.*

## Limitations

The callback benchmark is localhost-only, uses test-signed payloads, and does not measure VNPay network retries. P2 intentionally sends one independent callback per VU so that “independent payments” is not mixed with duplicate delivery; its effective throughput is therefore not comparable to P1. No live provider secret, production callback, JWT, card data, or user data was included in raw evidence.
